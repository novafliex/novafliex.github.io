Day 1｜HTTP 与网络基础

今天认识的 5 个术语，可以组成一条完整的网络请求链：

域名 → DNS → IP → 端口 → TCP → HTTP → Gin 服务

假设浏览器访问 http://api.example.com:8080/users，背后的过程可以简单理解为：

  1. DNS 将 api.example.com 解析为服务器 IP 203.0.113.10。
  2. 客户端找到服务器的 8080 端口。
  3. 客户端与服务器建立 TCP 连接。(如果是https还要建立TLS加密通道)
  4. 客户端发送 HTTP 请求。
  5. 请求进入 Gin Handler，处理完成后返回 HTTP 响应。

一、IP Address（IP 地址）

正式解释：

IP 地址用于标识网络中的主机或网络接口。

通俗理解：

IP 地址负责告诉请求：“应该去找哪台机器？”

例如，127.0.0.1 表示当前这台计算机，也就是本机。

二、Port（端口）

正式解释：

端口是传输层协议用来区分一台主机上不同网络服务的编号。

通俗理解：

IP 负责找到哪台机器，端口负责找到这台机器上的哪个程序。

项目例子：

r.Run(":8080") 表示 Gin 服务监听 8080 端口，等待客户端连接。

三、DNS（域名系统）

正式解释：

DNS 是一个分布式命名系统，最常见的作用是把域名解析为 IP 地址。

通俗理解：

人更容易记住域名，但计算机通信需要找到对应的 IP 地址。因此，DNS 就像网络中的通讯录：api.example.com → 203.0.113.10。

四、TCP（传输控制协议）

正式解释：

TCP 是一种面向连接、可靠并且保证数据顺序的传输层协议。

通俗理解：

找到 IP 和端口以后，客户端还需要和服务器建立连接。TCP 负责尽量保证数据能够送达，并且顺序正确。

HTTP/1.1 和 HTTP/2 通常运行在 TCP 之上。

五、HTTP（超文本传输协议）

正式解释：

HTTP 是一种应用层协议，用来规定客户端和服务器之间请求与响应的格式及通信方式。

通俗理解：

HTTP 规定了客户端应该怎样提问，服务器应该怎样回答。

Day 2｜HTTP 请求结构

今天认识的 5 个术语，可以组成一次完整的 HTTP 请求与响应：

URL 表示访问哪个资源 → Method 表示希望执行什么操作 → Header 携带认证方式、数据格式等附加信息 → Body 携带主要业务数据 → Status Code 表示服务器最终的处理结果

一、URL（统一资源定位符）

正式解释：

URL 用于描述网络资源的位置，以及访问这个资源所使用的方式。

通俗理解：

在互联网上找到特定网页、图片或数据的具体“网络地址” ,当前页面的 URL = 你当前在浏览器地址栏里看到的那一整串网址

https://api.example.com:443/courses?page=2

组成部分 示例 作用
Scheme https 使用什么协议访问
Host api.example.com 访问哪台主机
Port 443 访问主机上的哪个端口
Path /courses 访问哪个资源路径
Query page=2 补充请求参数

二、HTTP Method（HTTP 请求方法）

正式解释：

HTTP Method 用来表示客户端希望对目标资源执行的操作。

通俗理解：

增删改查(只是改有部分修改和全部之分)

后端最常见的方法：

Method 常见语义
GET 查询资源
POST 创建资源
PUT 整体更新资源
PATCH 部分更新资源
DELETE 删除资源

三、HTTP Header（HTTP 头字段）

正式解释：

HTTP Header 用来携带请求或响应的附加信息和元数据。

通俗理解：

请求头（Request Header）—— 客户端发给服务器，带上自己的身份和具体要求
响应头（Response Header）—— 服务器回给客户端，带上内容格式和后续指示（比如怎么缓存、存什么 Cookie）

常见 Header：

  • Authorization 常用于传递登录凭证。
  • Content-Type 说明消息体使用什么格式。
  • Accept 说明客户端希望接收什么格式的数据。

可以先记住：Header 保存附加信息，主要业务数据通常放在 Body 中。

四、HTTP Body（HTTP 消息体）

正式解释：

HTTP Body 用来携带请求或响应中的主要数据内容。

通俗理解：

Body 就像包裹里真正装着的东西，可以是用户提交的 JSON、表单，也可以是服务器返回的文字、图片或文件。

正式解释：

HTTP Status Code 是服务器在响应中返回的三位数字，用来表示请求的处理结果。

通俗理解：

状态码用于告诉客户端请求的处理结果。

Day 3｜请求参数与身份状态

Query Parameter → Path Parameter → Cookie → Session → JWT

今天的 5 个术语，可以放进下面这张关系图中：

一、Query Parameter（查询参数）

正式解释：

Query Parameter 是 URL 查询字符串中的键值参数，通常位于 ? 之后，用于向服务器补充筛选、排序、分页等请求条件。

通俗理解：

? 后面的每一个字(或直到锚点 # 出现之前)，都是用 & 串起来的“键值对数据”，全部属于查询参数

项目例子：

例如：https://api.example.com/courses?page=2&sort=price#reviews

  • page=2 和 sort=price 是 Query Parameter，使用 & 连接。
  • #reviews 是 Fragment（片段标识符），用于定位页面中的某个位置，不属于 Query Parameter。
  • 浏览器向服务器发送请求时，通常只会发送 # 前面的内容，不会把 #reviews 发送给后端。

二、Path Parameter（路径参数）

正式解释：

Path Parameter 是嵌入 URL 路径中的动态参数，通常用于标识某个具体资源或路由层级。

通俗理解：

用来精准定位“具体是哪一个东西”

项目例子：

例如，在 Gin 中先定义带有 :id 的路由：

客户端请求编号为 1001 的课程：

  • :id 表示路由中的 Path Parameter。
  • 请求 /courses/1001 时，c.Param("id") 得到的值是 1001。
  • /courses/1002 会匹配同一条路由，但读取到的 id 是 1002。

Tips：Path Parameter 和 Query Parameter 的区别

  • Path Parameter 通常用来定位一个具体资源。例如，/users/10086 表示访问 ID 为 10086 的用户，参数是路由结构的一部分；如果请求缺少这个 ID，/users/:id 通常无法匹配，并返回 404 Not Found。
  • Query Parameter 通常用来筛选、排序或分页。例如，/users?id=10086 表示先访问用户集合，再筛选出 id=10086 的用户；如果省略查询参数，请求 /users 通常会执行默认行为，例如返回用户列表。

简单记忆：Path 确定“访问哪个资源”，Query 补充“用什么条件查询”。

三、Cookie

正式解释：

Cookie 是由服务器设置或客户端创建、保存在用户代理中的小段数据；在满足域名、路径、有效期和安全策略等条件时，会随 HTTP 请求发送给服务器。

通俗理解：

Cookie 就像网站交给浏览器的一张小纸条。它可以记录登录身份的编号，也可以保存主题、语言等偏好；浏览器之后访问网站时，会按规则把这张纸条一起带上。

四、Session（会话）

正式解释：

Session 是在多次请求之间保存和识别用户状态的一种会话机制。服务器通常保存会话数据，并通过 Session ID 将请求与对应的会话关联起来。

通俗理解：

Session 是服务器为这张“电子通行证”在后台建的一份“私人档案袋”（或储物柜），用来真正存放你这段时间内的所有详细数据和操作记录

Tips：Cookie 和 Session 的核心区别

对比维度 Cookie Session
存放位置 保存在用户的浏览器中（客户端） 会话数据通常保存在服务器中（服务端）
安全性 用户可以查看或修改，后端不能直接信任其内容 核心数据不直接暴露给用户，但仍需保护 Session ID 和服务端存储
存放内容 少量数据，例如 Session ID、偏好设置 与会话相关的用户状态或业务数据
存储容量 较小，单个 Cookie 通常约为 4 KB，具体限制因浏览器而异 取决于服务器的存储方式和项目配置

简单记忆：Cookie 通常保存“通行证编号”，Session 保存这个编号对应的“后台档案”。

五、JWT（JSON Web Token）

正式解释：

JWT 是一种紧凑、URL 安全的令牌格式，用于在不同系统之间传递声明信息。JWT 通常由 Header、Payload 和 Signature 三部分组成，可通过签名验证内容是否被篡改，但默认不会加密 Payload。

通俗理解：

JWT 的本质是一张“带防伪签名的电子凭证”，不是默认加密的令牌。Header 和 Payload 中的内容通常可以被读取，所以密码、银行卡等隐私不能写进去；Signature 负责帮助服务器判断内容有没有被篡改。服务器可以不保存 Session，但是否记录登录状态或令牌黑名单，仍然由项目设计决定。

Day 4｜安全、连接与实时通信

HTTPS 依靠 TLS 保护通信｜Keep-Alive 复用连接｜CORS 控制跨域｜WebSocket 支持双向通信

今天的 5 个术语，可以放进下面这张关系图中：

一、HTTPS（超文本传输安全协议）

正式解释：

HTTPS 是运行在 TLS 安全通道之上的 HTTP，用于保护客户端与服务器之间传输的数据。

通俗理解：

给 HTTP 套上一层 TLS 安全外壳。传输中的 HTTP 内容会被加密并检查有没有遭到篡改，所以通信更安全。

项目例子：

当客户端访问 https://api.example.com/courses 时，请求内容会通过 TLS 加密后再传输。HTTPS 的默认端口通常是 443。

二、TLS（传输层安全协议）

正式解释：

TLS 是一种用于保护网络通信的加密协议，可以提供身份认证、数据机密性和数据完整性。

通俗理解：

TLS 是一套完整的安全协议——它不仅提供加密手段防偷看，还顺便把**身份验证（防冒充）和完整性校验（防篡改）**全给办了

项目例子：

浏览器访问 HTTPS 网站时，会在发送 HTTP 数据前与服务器进行 TLS 握手，并验证服务器证书。握手成功后，双方使用协商出的密钥加密后续通信。

三、Keep-Alive（持久连接）

正式解释：

Keep-Alive 是复用底层网络连接处理多个请求与响应的机制，可以减少重复建立连接带来的开销。

通俗理解：

打通电话后先别挂，有事接着说，省得每次都重新拨号

Tips：Keep-Alive 能保持多久？

Keep-Alive 连接能空闲多久，通常由 Web 服务器或 Nginx、CDN 等网络代理的超时配置决定，也可能受到客户端超时设置的影响。

四、CORS（跨源资源共享）

正式解释：

CORS 是一种基于 HTTP Header 的浏览器安全机制，服务器通过响应头声明哪些源可以跨域访问自己的资源。

通俗理解：

浏览器为了防坏人，默认不让你跨门串户；但如果对方主人贴了通行许可，浏览器就放行。

项目例子：

当前端运行在 http://localhost:3000，后端运行在 http://localhost:8080 时，两者属于不同的源。后端允许该前端访问时，可以返回：

对于某些跨域请求，浏览器会先发送 OPTIONS 预检请求，确认服务器允许后再发送正式请求。

五、WebSocket（全双工通信协议）

正式解释：

WebSocket 是一种在单个长连接上进行全双工通信的应用层协议，客户端和服务器都可以主动向对方发送数据。

通俗理解：

传统 HTTP 更像一问一答：客户端先问，服务器再回答。WebSocket 更像实时通话，连接建立后，客户端和服务器谁有消息都可以主动发送。

项目例子：

聊天、实时通知和在线状态等功能可以使用 WebSocket。连接通常先通过 HTTP 请求完成协议升级：

升级成功后，客户端与服务器可以在同一条连接上持续双向发送消息，不需要为每条消息重新发送一次普通 HTTP 请求。

Tips：HTTP 请求—响应与 WebSocket 的核心区别

维度 HTTP 请求—响应（通常由客户端发起） WebSocket（全双工）
通信模式 一问一答：客户端先发起请求，服务器再针对该请求返回响应。 随时双向互通：长连接建立后，客户端和服务器都能主动发送数据。
生活比喻 像在餐厅按铃叫服务员，按一次处理一次。 像两个人实时语音通话，双方随时都可以开口。
实时方案 通常使用轮询、长轮询或 SSE 等方式获取最新消息。 服务端有新消息时可以直接推送，适合聊天、通知等实时场景。
网络开销 每次请求和响应通常都需要携带 HTTP Header。 握手完成后使用较轻量的数据帧传输，但实际开销取决于帧长度、掩码和扩展。

Day 5｜数据库基础结构

一、Table（表）

正式解释：

Table 是关系型数据库中用于组织和存储同一类数据的结构，由列和行组成。每一列定义数据的字段，每一行保存一条具体记录。

通俗理解：

Table 就是把现实中某一类事物抽象出的“全部属性模版”及其“所有具体数据”给打包封装在一起的容器

二、Row（行）

正式解释：

Row 是表中的一条数据记录，由该表各列对应的值组成。

通俗理解：

在“结构”上必须是完整的一行数据（表有几列，这一行就必须对应几列），但在“内容”上允许某些非必填项留白（NULL）

三、Primary Key（主键）

正式解释：

Primary Key 是用于唯一标识表中每一行数据的列或列组合。主键值不能重复，也不能为 NULL。

通俗理解：

唯一标识(身份证号码)

四、Foreign Key（外键）

正式解释：

Foreign Key 是表中的一个列或列组合，用来引用另一张表中的主键或唯一键，从而建立表之间的关联并维护引用完整性。

通俗理解：

单子上不抄对方容易变的详细信息（如住址），只留一个对方的“唯一编号”（外键）；发货时顺着编号一查，永远能拿到他最新的实时数据

项目例子：

这样，课程中的 teacher_id 必须对应 users 表中真实存在的用户。

Tips：主键和外键的区别

主键负责唯一标识“自己表中的这一行”，外键负责指向“另一张表中的某一行”。主键不能重复，外键可以重复，例如同一名教师可以拥有多门课程。

五、Constraint（约束）

正式解释：

Constraint 是数据库为表中数据规定的校验规则，用于阻止不符合要求的数据被写入，从而保证数据的正确性和一致性。

通俗理解：

限制条件，比如不能为空、不能重复、必须满足指定条件等等。

项目例子：

  • NOT NULL：值不能为空。
  • UNIQUE：值不能重复。
  • CHECK：值必须满足指定条件。
  • PRIMARY KEY 和 FOREIGN KEY 也属于约束。

Day 6｜数据库字段与唯一性

一、Schema（模式）

正式解释：

Schema 是数据库中用于组织表、视图、索引等对象的逻辑命名空间，可以帮助划分和管理不同业务的数据结构。

通俗理解：

数据库中的建表规划图,但是还没有写如任何数据,只有建几个表格,表格保留哪些字段,每个字段都有什么数据类型,字段是否为空,字段是否唯一,字段是否为索引等等

PostgreSQL 可以在一个数据库中创建多个 Schema；在 MySQL 中，Schema 基本可以理解为 Database 的同义词。

二、Data Type（数据类型）

正式解释：

Data Type 用来规定一列能够保存的数据形式、取值范围以及可以执行的操作。

三、NULL（空值）

正式解释：

NULL 表示某个字段的值缺失、未知或暂时不适用。它不等于数字 0、空字符串 ''，也不等于另一个 NULL。

Tips：判断 NULL

判断 NULL 要使用 IS NULL 或 IS NOT NULL，不能使用 = NULL 或 != NULL。

四、Unique Index（唯一索引）

正式解释：

Unique Index 是不允许索引键值重复的索引，既可以加快查询，也可以由数据库保证指定列或列组合的唯一性。

五、Composite Key（复合键）

正式解释：

Composite Key 是由两个或多个列共同组成的键。只有把这些列组合起来，才能唯一标识一行数据。

通俗理解：

Day 7｜数据库索引与查询计划

一、Index（索引）

正式解释：

Index 是数据库为了加快数据查找而维护的辅助数据结构，保存索引键与对应数据位置之间的关系。

二、B+ Tree（B+ 树）

正式解释：

B+ Tree 是一种多路平衡树。它的非叶子节点主要保存索引键和子节点指针，叶子节点按顺序保存索引记录，适合数据库的等值查询和范围查询。

三、Full Table Scan（全表扫描）

正式解释：

Full Table Scan 是数据库依次读取表中大量或全部数据行，再判断哪些行满足查询条件的访问方式。

通俗理解：

在没有导航目录时(除了全部查找没有更快的方法了),需要查找指定的数据,对所有的数据进行全部查找

项目例子：

Tips：全表扫描不一定是错误

当表很小，或者查询本来就要读取大部分数据时，数据库主动选择全表扫描可能比频繁访问索引更合适。

四、Query Plan（查询计划）

正式解释：

Query Plan 是数据库优化器为执行一条 SQL 选择的具体方案，包括表的访问方式、使用的索引、连接顺序以及预计读取的数据量等信息。

高级的筛选器，可以有效提高查询效率

Day 8｜数据库事务与并发控制

一、Transaction（事务）

正式解释：

Transaction 是数据库中的一组操作，它们被当作一个不可分割的工作单元执行：要么全部提交成功，要么在失败时全部回滚。

项目例子：

如果第二条更新失败，应执行 ROLLBACK，避免只扣款却没有收款。

二、ACID（事务的四个基本特性）

正式解释：

ACID 是衡量事务可靠性的四个基本特性：Atomicity（原子性）、Consistency（一致性）、Isolation（隔离性）和 Durability（持久性）。

通俗理解：

原子性 —— “同生共死” 一致性 —— “守恒原则” 隔离性 —— “互不干扰” 持久性 —— “落子无悔”

项目例子：

  • 原子性：扣款和收款要么都成功，要么都失败。
  • 一致性：事务前后都要满足余额、约束等业务与数据库规则。
  • 隔离性：并发转账时，各事务不能随意看到对方尚未提交的数据。
  • 持久性：提交成功后，即使数据库重启，结果也不能丢失。

三、Isolation Level（隔离级别）

正式解释：

Isolation Level 用来规定并发事务之间能够看到哪些数据变化。SQL 标准从弱到强定义了 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ 和 SERIALIZABLE 四个级别。

通俗理解：

项目例子：

隔离级别越强，并发事务之间的干扰通常越少，但等待和并发控制成本可能越高。不同数据库对各级别的具体实现并不完全相同。

四、Lock（锁）

正式解释：

Lock 是数据库协调并发访问的机制。当事务修改或锁定数据时，数据库可以阻止其他冲突操作同时进行，从而避免数据被并发破坏。

项目例子：

FOR UPDATE 会对目标数据加排他性质的锁。其他事务若要修改同一数据，通常需要等待当前事务提交或回滚。

五、MVCC（多版本并发控制）

正式解释：

MVCC（Multi-Version Concurrency Control）是数据库通过保存数据的多个版本，让事务按照自己的可见性规则读取合适版本的并发控制机制。它可以减少普通读取与写入之间的相互阻塞。

项目例子：

事务 A 正在修改账户余额但尚未提交时，事务 B 的普通查询可以根据数据库的隔离规则读取一个已提交的旧版本，而不一定要等待事务 A 完成。

Tips：Lock 和 MVCC 不是二选一

数据库通常会同时使用锁和 MVCC。MVCC 主要改善普通读写并发，写写冲突、显式锁定读取等场景仍然需要锁来协调。
